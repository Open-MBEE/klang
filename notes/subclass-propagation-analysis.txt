ANALYSIS: Subclass Instance Count Propagation
=============================================
Date: 2026-01-18

PROPOSED CHANGE:
----------------
Propagate instance counts from parent classes to subclasses during heap layout.
When we have `var leftExp: S_Exp` and Atom/ListExp extend S_Exp, ensure each 
subclass has at least as many instances as the parent.

Rationale: A reference to S_Exp can hold any subclass, so we need enough 
subclass instances to cover all parent references.

After Change (uncommitted):

CONCLUSION:
-----------
The propagation approach has a critical flaw: it can INCREASE search space
unnecessarily, causing timeouts on tests that previously passed.

The HeapCEGAR loop already handles under-allocation by increasing multiplier.
Pre-allocating extra instances is counter-productive when the initial 
allocation is sufficient.

Additionally, the lisp.k issue was ALREADY FIXED by commit 664f571 
("Fix HeapCEGAR: use strategy 1 for DFS and fix multiplier ordering").
The propagation change was unnecessary - lisp.k passes without it!

RECOMMENDATION:
---------------
DISCARDED this change. The lisp-draft.k regression is unacceptable and
the change was solving an already-solved problem.

Alternative approaches to explore (if ever needed in future):
1. Allow parent slots to hold child objects (polymorphic heap slots)
   - See stash "polymorphic-heap-slots-approach"
2. Use "used" flags to make extra instances optional
3. Only propagate when HeapCEGAR indicates UNSAT with all-full heap
