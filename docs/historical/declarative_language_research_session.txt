The question is really: how do we know we’re in a “spec place” vs ordinary code? Annotations (or some explicit marker) are mainly about making that boundary unambiguous and giving both the user and the engine control.
Let me break down where annotations buy you something, and where you can safely get away without them.

1. Not every Boolean is a “constraint”
In a host language (Java/Python/etc.), Booleans show up everywhere:
if (x > 0 && y > 0) { ... } boolean ok = x > 0 && y > 0; return (size > 0) && ready(); 
You don’t want to interpret all of these as global logical constraints (things that must hold across all executions and models):
	•	if (x > 0) is a branch guard. In symbolic execution you treat it as a path condition (“on this branch, assume x > 0”), not as a global invariant.
	•	boolean ok = ... is just building a Boolean value; that expression might be used later in a purely computational way.
	•	return (size > 0) && ready(); might be a function whose result you want to constrain elsewhere, but you don’t know that from this call site alone.
So you essentially have three kinds of Boolean usage:
	•	Path conditions (if, while guards): local path constraints, not global invariants.
	•	Computed Booleans: “ordinary data,” not automatically a constraint.
	•	Specs / invariants / constraints: properties the programmer wants the solver to reason about as facts.
Without some marker, it’s easy to blur (2) and (3).

2. The minimal role of annotations: “this is a spec context”
You don’t need annotations on every Boolean; you need a way to say:
“Everything Boolean in here is being written as a spec, not as ordinary code.”
That can be as big or as small as you like:
	•	Big-grain: a whole block or function:
@ConstraintBlock void model() { x > 0 && y > x; // purely declarative // … maybe syntactically restricted } 
Inside this block, any Boolean expression is taken as a constraint, no extra annotation.
	•	Small-grain: specific declaration:
@Invariant boolean sizeNonNegative() { return size >= 0; } @Pre boolean requiresNonEmpty() { return !list.isEmpty(); } 
Here, the annotation lives on the method or block, not on every Boolean subexpression. That’s usually enough: it tells the compiler “rediscover everything inside as constraints.”
Advantages:
	•	You separate “I’m computing” from “I’m declaring a property.”
	•	The engine can enforce restrictions in spec contexts (e.g., “no side effects,” “no opaque calls unless explicitly allowed,” etc.).
	•	The solver backend knows where to look for constraints instead of treating all Booleans in the program as specs.

3. Ambiguous cases without an explicit marker
Here are some concrete cases where intent is genuinely unclear without annotations or a spec keyword.
3.1 Boolean-returning helper vs invariant

	•	treat every call to ready() in a spec context as a constraint term;
	•	treat other calls as computation.

The front-end now knows this method is intended to be purely logical and exportable into constraints.
3.2 “assert”, “assume”, vs “constraint”
In a solver-aided language, these are different:
	•	assume P: extend the current constraint set with P (hypothesis).
	•	assert P: check that P follows from the current constraint set (verification).
	•	“constraint P”: P is part of the model that needs to be satisfied or solved for.
If you just see if (P) or boolean b = P, you don’t know which semantics the user intended.

@Assumption boolean ageKnown() { return age != UNKNOWN; } @Constraint boolean ageAtLeast18() { return age >= 18; } void step() { assert age >= 0 : "sanity check"; // runtime assertion, not a logical spec }

No solving logic here—just structure and metadata.

3.2 Layer 2 – AST → IR compilation
This is the bridge:
	•	Implement a compiler from each front-end AST to the shared IR we sketched:
	•	create Symbols for variables and fields,
	•	turn guards/spec methods into Constraints,
	•	turn activity classes into ActivityInstance IR templates,
	•	translate if/while into IR statements with explicit branch nodes,
	•	mark opaque host calls (uninterpreted or with an SMT encoding id).
Key point: this compilation is structural and testable. No reflection, no runtime codegen. Once you have IR, the original Java/K/Python can disappear.

3.3 Layer 3 – Core symbolic engine (“new BAE”)
Implement BAE as a pure engine over IR, with:
	•	Symbolic state:
	•	mapping from SymbolId → current (maybe-symbolic) term or value,
	•	heap of HeapObjects,
	•	registry of TVMInstances and ActivityInstances.
	•	Constraint store:
	•	central ConstraintStore with tags (Domain_String, Domain_Scheduling, Solver_Friendly, etc.).
	•	Execution semantics:
	•	interpreter for IR Stmt:
	•	Assume → add constraint,
	•	Branch → create choice points with path conditions,
	•	Call → either:
	•	inline spec / pure function as IR,
	•	call out to solver if it’s a “query” function,
	•	or do a concrete opaque call when appropriate.
	•	BAE-style search loop:
	•	maintain a worklist of states,
	•	at each choice point, either:
	•	let the engine guess (non-det choice),
	•	or ask a solver to choose a satisfying extension.
	•	Planning/scheduling support:
	•	operations over ActivityInstance & TimeVaryingMap:
	•	primitives like “post precedence constraint”, “resource capacity constraint”.
	•	domain-specific heuristics to build schedules, possibly before/after calling SMT.
Crucially, this engine never sees Java/Python classes at all, only IR.

3.4 Layer 4 – Solver adapters
Design a small, clean solver interface:
	•	IR slice → solver query, solver result → IR model updates.
Features:
	•	Subset selection:
	•	query only constraints tagged as solver-friendly and in particular domains (arith+string+time, etc.).
	•	Timeouts & unknown handling:
	•	give solvers time budgets per query,
	•	handle unknown / timeout by:
	•	logging,
	•	keeping constraints as “unchecked”,
	•	proceeding with heuristic search.
	•	Multiple backends (future):
	•	Today: Z3 adapter (using its modern string, array, sequence theories).
	•	Tomorrow: CP/MiniZinc adapter for slices that are obviously finite-domain scheduling.
This layer should depend only on IR types and solver APIs; swapping Z3 for something else shouldn’t touch the engine.

4. How this differs from old BAE in practice
Old BAE:

	•	“Execution” and “representation” are entangled; solver and Java semantics are tightly mixed.
New architecture:
	•	K/Java/Python → AST → IR → engine → solvers.
	•	Reflection optional and localized (if you use it at front-end boundary or for opaque calls).
	•	Much easier to:
	•	plug new surface languages,
	•	refactor the solver layer,
	•	unit-test the core engine with synthetic IR programs.
